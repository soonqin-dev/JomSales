# 登录与注册规格（AUTH）V1

日期：2026-10-07。读者：负责 UI/UX 的人，以及负责实现的 Codex。

依据：`JomSales-UIUX-代号总表-v1`、Figma 的 Log In / Sign Up 稿、负责人 2026-10-07 的三项决定，以及 `soonqin-dev/jomsales` main 分支的现有代码（`app/account/page.js`、`app/auth/*`、`app/join/page.js`、`app/settings/page.js`、`lib/account-utils.js`、迁移 `202610060001`）。

代号沿用总表。网址不新增：登录、注册、等待页都在 `/account`，不为每个画面开新路由。

## 0. 已确认的决定

1. **WhatsApp 在注册时必填**（第 2 步）。注册后仍可在个人资料（PRO，现为 `/settings`）更改。
2. **登录后的去向**：没有公司 → 等待页 `AUTH.WAIT`；有公司 → 直接进入产品目录（`CAT`，`/cloud`）。姓名、WhatsApp、邮箱、密码在注册时一次收齐，所以正常路径**不再出现** `AUTH.PROFILE_FIRST`。
3. **密码最少 6 个字符，最多 128**。沿用 `PASSWORD_MIN_LENGTH`，不改常量。

### 对代号总表的修订（合并时同步）

- `AUTH.REGISTER` 增加 `AUTH.REGISTER.WHATSAPP`，步骤顺序为姓名 → WhatsApp → 邮箱 → 密码。
- `AUTH.PROFILE_FIRST` 降级为"旧账号补资料保护"，只给注册时没有 WhatsApp 的老账号用，见 5.7。
- `AUTH.REGISTER` 的保护说明"不能自行创建公司或注册管理员"保持不变。

## 1. 现状与目标

| 项目 | 现状（代码） | 目标 |
|---|---|---|
| 注册 | `/account` 页内的"登录／注册"切换，一页收姓名、邮箱、密码，不收 WhatsApp | 4 步向导，仍在 `/account` |
| WhatsApp 存储 | 触发器 `jomsales_seed_profile` 只读 `display_name`，WhatsApp 只能注册后在 `/settings` 填 | 注册时一并存入，需要新迁移（见 6.1） |
| 登录错误 | 直接显示 Supabase 返回的原文 | 中文通用提示（见 5.1） |
| 忘记密码、重发验证 | 两个按钮常驻在表单下，邮箱为空时置灰 | 按 5.1、5.3 的规则显示，并加倒计时 |
| 等待公司 | 是 `/account` 已登录视图里的一行文字 | 独立的 `AUTH.WAIT` 画面 |
| 登录后跳转 | `window.location.replace(hasInvite ? "/join" : "/")`，`/` 由服务端检查登录后 `redirect("/cloud")` | 保持，见第 2 节 |
| 新密码确认框 | 注册没有，重置和账号安全有 | 注册用显示/隐藏开关（Figma 如此），重置保留确认框 |

## 2. 登录后去向（判断顺序）

登录成功（含邮箱验证回调成功）后，按以下顺序判断，命中即停：

1. **有待接受的邀请**（`pendingInvite()` 有值）→ `/join`。保持现有行为。
2. **读取公司失败** → 留在原画面显示 `ST.ERROR` 和"重新读取"。**读取失败不能显示等待页**，否则会让有公司的人误以为被移除。现有代码已用 `membershipLoaded` 区分，保持。
3. **没有任何有效公司** → `AUTH.WAIT`。
4. **有公司但资料不全**（仅旧账号） → `/settings?setup=company&next=…`。这是 `companyProfileReady` 现有的保护，保留，不删。
5. **其余** → `/cloud`（产品目录）。多公司时的选择沿用现有 `?company=` 机制，本规格不改。

"有公司"指 `company_members.active = true` 且未被移除。被停用的成员按"没有公司"处理，但文案要区分（见 5.6）。

## 3. 通用规则

- 所有文案用简体中文，不显示 Supabase 的英文原文。
- 邮箱统一 `trim()`，比较时不分大小写。
- 密码不记录、不放进网址、不写入浏览器存储。提交成功后立即清空。
- 步骤之间的输入保存在页面内存里，返回上一步不丢失；刷新页面会清空，这是可接受的。
- 防重复提交：提交期间按钮置灰并显示"处理中…"，沿用现有 `busy`。
- 不泄露账号是否存在：忘记密码、重发验证、注册重复邮箱的提示都用同一类措辞。
- 触控区域至少 44×44 px，"忘记密码？"也一样。
- 输入框要有正确的 `type`、`inputMode`、`autoComplete`，让手机密码管理器可用（见各画面）。

## 5. 各画面规格

### 5.1 AUTH.LOGIN 登录

内容：Logo、`AUTH.LOGIN.EMAIL`、`AUTH.LOGIN.PASSWORD`（带显示/隐藏）、`AUTH.LOGIN.SUBMIT`、`AUTH.LOGIN.FORGOT`、`AUTH.LOGIN.REGISTER`。

字段：
- 邮箱：`type="email"`，`autoComplete="email"`，`inputMode="email"`，最长 254。
- 密码：`autoComplete="current-password"`，登录时 **不做最小长度校验**（兼容旧账号，沿用 `minLength={1}`），最长 128。

文案：
- 主按钮：`登录`；提交中 `处理中…`。
- 次按钮：`注册员工账号`（Figma 现为"创建新账号"，改掉，避免老板以为能自己开公司）。
- 注册按钮下方一行小字：`收到邀请的员工，请用邀请链接加入。`
- `忘记密码？` 为文字链接。

状态：

| 状态 | 触发 | 表现 |
|---|---|---|
| 默认 | — | 如上 |
| 提交中 | 点登录 | 按钮和输入框禁用 |
| 密码错误 | 账号或密码不对 | 表单上方 `G.INLINE_ERROR`：`邮箱或密码不正确。` 不区分是哪一个 |
| 邮箱未验证 | Supabase 返回 `email_not_confirmed` | 提示：`这个邮箱还没有验证。请先点开验证邮件里的链接。` 下方出现 `重新发送验证邮件`（带倒计时，见 5.3） |
| 请求过多 | Supabase 返回限流 | `尝试次数过多，请稍后再试。` |
| 网络错误 | 请求失败 | `无法连接，请检查网络后重试。` |
| 邀请中 | `pendingInvite()` 有值 | 页面顶部一条提示：`你正在接受公司邀请，请用受邀邮箱登录或注册。` 并保留"返回邀请"链接（`AUTH.LOGIN.RETURN_INVITE`） |

忘记密码（`AUTH.LOGIN.FORGOT`）：
- 邮箱为空：不发请求，在邮箱框下提示 `请先在上面输入邮箱。` 并聚焦邮箱框。按钮**不置灰**，置灰的按钮没有解释。
- 邮箱已填：调用 `resetPasswordForEmail`，`redirectTo` 为 `${origin}/auth/reset`。
- 成功后无论该邮箱是否存在，统一显示：`如果这个邮箱已注册，你会收到一封重置邮件。请在这台手机的同一个浏览器里打开链接。` 并启动 60 秒倒计时，期间忘记密码不可再点。

### 5.2 AUTH.REGISTER 注册（4 步向导）

整体：
- 每一步一个问题，顶部有返回箭头（`G.BACK`），第 1 步的返回回到登录。
- 加步骤进度，例如 `1 / 4`，放在标题上方。Figma 目前没有，要补。
- 向导状态只存在页面内存；第 4 步提交成功后进入 `AUTH.VERIFY` 的"待验证"状态。

| 步骤 | 代号 | 标题 / 提示 | 字段与校验 | 按钮 |
|---|---|---|---|---|
| 1 | `AUTH.REGISTER.NAME` | `你的姓名` / `请输入你工作中的名字。` | `autoComplete="name"`，去首尾空格后 1–120 字符 | `下一步` |
| 2 | `AUTH.REGISTER.WHATSAPP` | `你的WhatsApp号` / `请输入你工作中使用的WhatsApp号码。` | 见下方号码规则 | `下一步` |
| 3 | `AUTH.REGISTER.EMAIL` | `你的邮箱` / `请输入你工作中使用的邮箱。` | `type="email"`，`autoComplete="email"`，最长 254 | `下一步` |
| 4 | `AUTH.REGISTER.PASSWORD` | `你的密码` / `请创建至少包含 6 个字符的密码。` | `autoComplete="new-password"`，6–128 字符，带显示/隐藏 | `注册并验证邮箱` |

**WhatsApp 号码规则（第 2 步）**
- 界面显示固定的 `+60` 前缀加输入框（沿用 Figma），输入框 `type="tel"`，`inputMode="tel"`，`autoComplete="tel-national"`。
- 提交前规范化：去掉空格、括号、连字符；如果用户输入以 `0` 开头（如 `012 345 6789`），去掉这个 `0`，再加 `+60`。
- 规范化后必须匹配现有规则 `^\+[1-9][0-9]{7,14}$`（与 `lib/account-utils.js` 及数据库约束一致）。
- 错误提示：`请输入正确的手机号码，例如 12 345 6789。`
- 第 2 步在这里是**必填**。`profileFields()` 现在允许空号码，注册流程要额外要求非空。
- 小字提示：`顾客通过你分享的链接联系你时会用到这个号码。之后可在"我的"里更改。`

**第 4 步密码**
- 提示行下方加一条弱提示（不拦截）：`建议使用更长、且不与其他网站重复的密码。`
- 本规格按负责人决定采用 6 字符。Supabase 官方不建议低于 8 位，记录在 `docs/password-minimum.md`，此处不改变决定。

**提交（第 4 步）**
- 调用 `signUp`，`data` 里带 `display_name` 和 `whatsapp`（规范化后的 E.164），`emailRedirectTo` 为 `${origin}/auth/callback`。
- 成功且没有 session（邮箱验证开启，正常情况）→ 进入 `AUTH.VERIFY` 待验证状态。
- 成功且已有 session（不应发生，说明 Supabase 关了邮箱确认）→ 按第 2 节登录后去向处理，并在日志里留下警告。
- 邮箱已注册：Supabase 开启确认时不会报错，会照常显示待验证页。待验证页文案要覆盖这种情况（见 5.3），不要单独提示"邮箱已存在"。
- 密码太短：在第 4 步的字段下用 `G.INLINE_ERROR` 提示 `密码至少需要 6 个字符。`
- 号码或姓名不合法：回到对应步骤并定位到错误。

保护：不能在这里创建公司，也不能注册管理员。

### 5.3 AUTH.VERIFY 邮箱验证

**待验证状态**（`/account`，注册提交后）：
- 标题：`验证邮箱`
- 内容：`注册申请已提交。请检查 {邮箱} 的收件箱，包括垃圾邮件，验证后回来登录。`
- 再加一句：`如果这个邮箱之前已经注册过，请直接登录。`
- 按钮：`返回登录页面`（次要）、`重新发送邮件`（主要）。
- 重发：调用 `resend({ type: "signup" })`，成功后提示 `验证邮件已重新发送，请稍候查看。` 并启动 60 秒倒计时，按钮显示 `{n} 秒后可重发`。
- 可选：加一个 `打开邮箱` 链接，指向 `mailto:`，成本低。是否做由负责人定。

**结果状态**（`/auth/callback`，已有页面，仅补状态）：

| 状态 | 条件 | 表现 |
|---|---|---|
| 处理中 | 正在确认 | `正在确认邮箱验证结果…` |
| 成功 | `getUser()` 成功 | 现有逻辑：有邀请跳 `/join`，否则跳 `/account`。新增一个短暂的成功提示 `邮箱已验证。`，之后再按第 2 节判断去向 |
| 链接无效或过期 | URL 带 `error` | `验证链接无效或已过期。` 并提供 `重新发送验证邮件`（需要用户输入邮箱，因为此时没有上下文） |
| 无法确认 | 其他 | `请返回登录页尝试登录。` 常见原因是在**另一个浏览器**打开了链接（PKCE），要明说：`如果你是在别的浏览器打开的链接，直接回来用邮箱和密码登录即可。` |

### 5.4 AUTH.RESET 重置密码

网址 `/auth/reset`，页面已存在，仅补状态与文案。

内容：`AUTH.RESET.PASSWORD`、`AUTH.RESET.CONFIRM`（**保留确认框**，重置是高风险操作）、`AUTH.RESET.MFA`（仅在账号启用了验证器时显示）、`AUTH.RESET.SUBMIT`、`AUTH.RESET.LOGIN`。

| 状态 | 表现 |
|---|---|
| 检查链接中 | `正在检查链接…` |
| 可设置 | 表单，提示 `新密码（6–128 个字符）` |
| 链接失效 | `链接失效或尚未登录。请重新申请重置邮件，并在同一浏览器打开。` 带 `返回登录` |
| 两次不一致 | `两次输入的密码不一致。` |
| 验证码错误 | `验证码不正确，请重试。` |
| 提交中 | 按钮禁用 |
| 完成 | 现有逻辑：全设备退出后跳 `/account`。新增在登录页顶部显示一次 `密码已更新，请用新密码登录。` |
| 退出未确认 | 沿用现有文案：`密码已修改，退出设备未确认。请返回账号页重新登录。` |

### 5.5 AUTH.JOIN 接受邀请

`/join` 已存在，规格只补状态，不改流程。

| 状态 | 表现 |
|---|---|
| 未登录 | `请先登录受邀邮箱`，带 `登录／注册`。注册时 `pendingInvite()` 已保留邀请 |
| 邀请有效、邮箱匹配 | 显示公司、受邀邮箱、角色，主按钮 `接受邀请并加入公司` |
| **邮箱不匹配** | 同时显示"受邀邮箱"和"当前登录邮箱"，说明：`这个邀请是发给 {受邀邮箱} 的。你现在登录的是 {当前邮箱}。` 主按钮改为 `换账号`（`AUTH.JOIN.CHANGE_ACCOUNT`），不显示接受按钮。这是员工最容易卡住的地方 |
| 已过期 / 已撤销 / 无效 | `邀请已失效。请联系公司管理员重新发送。` 不泄露公司私有资料 |
| 已接受过 | 现有文案：重新确认当前权限 |
| 成功 | `已加入公司`，按钮 `进入公司`，进入 `/cloud?company=…` |

### 5.6 AUTH.WAIT 等待公司邀请

条件：已登录、读取公司成功、没有任何有效公司、没有待接受邀请。

内容：
- `AUTH.WAIT.IDENTITY`：显示当前登录邮箱。
- 标题：`等待公司邀请`
- `AUTH.WAIT.MESSAGE`：`你的账号已创建。请让公司管理员给你发送邀请链接，打开链接即可加入公司。`
- 如果该账号**曾经有公司但已被停用或移除**（`company_members` 有记录但不再有效）：改为 `你对原来公司的访问已停用。如有疑问，请联系公司管理员。` 不要让这类用户以为自己是新账号。
- 按钮：`重新读取`（`AUTH.WAIT.RELOAD`）、`个人资料`（`AUTH.WAIT.PROFILE`，去 `/settings`）、`退出登录`（`AUTH.WAIT.LOGOUT`）。
- **不提供创建公司的入口**。公司由平台负责人开通。

### 5.7 AUTH.PROFILE_FIRST 旧账号补资料（保留的保护）

正常注册的账号不会看到这个画面。它只服务于在本次改动之前创建、`account_profiles.whatsapp` 为空的老账号。

- 触发：现有的 `companyProfileReady()` 返回 false 时，`/cloud`、`/team` 等页面把用户送到 `/settings?setup=company&next=…`。**这个机制不改**。
- 画面复用 `/settings` 的"姓名与工作号码"表单（PRO），顶部提示沿用：`进入公司前请补齐姓名和工作 WhatsApp。只需设置一次，之后可直接使用。`
- 保存后出现 `继续进入公司`。

### 5.8 改号码（PRO，现有行为，仅确认）

注册后更改 WhatsApp 沿用 `/settings` 现有逻辑，不新增：
- 如果原来已有号码，改成新号码时弹确认（`D.PHONE_CHANGE`）：`更改工作 WhatsApp 会永久撤销你在所有公司的旧顾客目录链接；改回旧号码也不会恢复。确认更改？`
- 保存成功后提示旧链接已撤销、需要重新生成。
- 号码规范化规则与 5.2 一致。

## 6. 实现说明（给 Codex）

开工前：先读 `AGENTS.md`，再按它的要求阅读 `node_modules/next/dist/docs/` 里相关的 Next.js 文档，再动手。这个版本的 Next.js 有破坏性变更。

### 6.1 数据库：新增迁移

新建 `supabase/migrations/202610070002_register_whatsapp.sql`，替换 `jomsales_seed_profile()`：

- 从 `raw_user_meta_data->>'whatsapp'` 读取号码。
- 只有当号码匹配 `^\+[1-9][0-9]{7,14}$` 才写入；否则写空字符串，**不让注册失败**（避免阻塞账号创建）。
- `display_name` 的现有处理保持（超过 120 字符置空）。
- 函数仍是 `security definer`，`set search_path=''`，权限保持 `revoke all`。
- 只影响**新**账号，不改已有数据，不重置已有号码。

新增 `supabase/tests/register_whatsapp.sql`，覆盖：合法号码被存入；非法号码被存为空；没有 `whatsapp` 元数据时为空；`display_name` 行为不变；已有账号的资料不变。

README 的"Rollout"一节要加上这条迁移的执行说明，格式与现有迁移说明一致：只执行一次，说明是新增迁移。

### 6.3 Supabase / 部署配置（不是代码，需要人工核对）

1. **Minimum password length** 要设为 6，与前端一致。见 `docs/password-minimum.md`。
2. **Redirect URLs** 必须同时包含：`/auth/callback` 和 **`/auth/reset`**，每个都要有生产域名和 `http://localhost:3000` 两个版本。README 现在只列了 `/auth/callback`，且域名还是旧名 `salesgo-tool.vercel.app`，与线上的 `jomsales.vercel.app` 不一致。如果漏了 `/auth/reset`，重置邮件的链接可能跳到错误页面。
3. 保持邮箱确认开启。
4. 验证邮件和重置邮件的 Supabase 邮件模板要改成中文，否则员工收到英文邮件。这属于后台配置，不在代码里。

### 6.4 完成标准

- [ ] 能用 4 步完成注册，WhatsApp 必填，规范化后以 `+60…` 形式存入 `account_profiles.whatsapp`。
- [ ] 新注册账号验证邮箱、登录后，不会被送去 `/settings?setup=company`。
- [ ] 无公司账号登录后看到 `AUTH.WAIT`；有公司账号登录后直接到 `/cloud`。
- [ ] 读取公司失败时不会显示等待页。
- [ ] 5 个字符的密码被拒绝，6 个字符可以注册（注册、重置、账号安全三处一致）。
- [ ] 登录错误没有英文原文，也不区分"邮箱不存在"和"密码错误"。
- [ ] 忘记密码、重发验证邮件有 60 秒倒计时，且对已注册和未注册邮箱显示同样的提示。
- [ ] 邀请邮箱不匹配时显示"换账号"，不显示接受按钮。
- [ ] 旧账号（无 WhatsApp）仍被正确送去补资料。
- [ ] `npm test`、`npm run build`、`npm run check:supabase` 通过。
- [ ] 新迁移在隔离的测试数据库里跑过，没有改动生产数据。
